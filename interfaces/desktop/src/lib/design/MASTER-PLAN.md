# ColdLight Design System -- Master Plan

> **@devpulse/coldlight** v0.3.0 (Updated 2026-02-21)
> Schema-registry-driven design system, component library, and block composition engine.
> Taxonomy-first architecture: typed contracts, Zod-validated boundaries, four runtime registries (recipes, blueprints, patterns, blocks).
> Contracts live WITH their implementations — `primitives/*/contract.ts` and `components/*/contract.ts` declare themselves into the taxonomy registry at build time.
> Every UI entity — primitive, surface, composition, page section — exists only if its contract.ts is present with its implementation and registered in the taxonomy manifest.
>
> **ColdLight is a portable, multi-project, UI-driven design system** owned by the architect. Deployed across the architect's own projects and customer engagements. Config-first: `coldlight.config.ts` is project-specific. VPB reads config + manifest to present configuration UI.
>
> **ColdLight is the sole authority.** The human owner directs ColdLight. ColdLight directs all CSS, all components, all generation. No library, no tool, no AI agent overrides the owner's decisions. Configuration is the owner's instrument of control -- `coldlight.config.ts` declares what exists, what gets generated, and what gets enforced. Code serves the config. Config serves the owner.
>
> Visual identity: liquid surfaces, particle effects, metal/glass/molten aesthetics, OKLCH color system, dark-first.
> Named for Tesla's cold light gas tubes (1890s).

## Core Terminology (Locked)

### The Four Registries

| Registry | Runtime? | What It Contains | Where It Lives |
|----------|----------|------------------|----------------|
| **Recipe** | Yes | CSS appearance rules: surfaces, layered bevels, pseudo-elements, motion/transition toggles | `recipes/` |
| **Blueprint** | Yes | Composition defaults + slot wiring: typed "how this component is assembled" -- slots, default props, child-prop inheritance, which recipe hooks apply by default | `blueprints/` |
| **Pattern** | No | Documentation guidance only: usage rules, do/don't, accessibility notes, examples | `patterns/` |
| **Block** | Yes | Runtime VPB payload: serializable object that VPB saves/loads | `blocks/` (schemas + renderers) |

Each registry has typed IDs. If it isn't registered, it doesn't exist.

### Provider Model (Industry-Correct)

| Term | Definition |
|------|-----------|
| **ColdLight-Owned (DEFAULT)** | ColdLight directly owns `role`, `aria-*`, `tabindex`, focus management, keyboard navigation. Native WAI-ARIA APG patterns. No adapter needed. |
| **Provider Adapter** (`dsAdapter`) | EXCEPTION ONLY — ColdLight's integration layer mapping Melt UI APIs to ColdLight's API + `data-kind`/`data-slot`/`data-state`. Used only when ARIA/focus/keyboard complexity genuinely justifies adapter overhead. |
| **Provider Internals** | The adapter-specific implementation boundary at `api/adapters/meltui/_internal/`. ColdLight public API never exposes these. |

ColdLight owns ARIA by default. Components NEVER import `@melt-ui/svelte` directly. The dsAdapter transport chain cloaks the dependency for the rare exceptions that need it.

### Two Primitive Archetypes

**Archetype A: ColdLight-Owned (DEFAULT)** (`ariaStateProvider: "coldlight"`)
Component renders native HTML with ARIA computed and applied in the `components/` layer. No adapter. Primitive layer is zero-ARIA — it only passes `aria-*` through via `...rest` spread. Component layer computes ARIA from state props and applies it. **This is the default for ALL new primitives.** ColdLight owns ARIA, state, keyboard, focus via WAI-ARIA APG patterns. Only escalate to Archetype B when the ARIA/focus/keyboard complexity genuinely justifies adapter overhead (e.g., complex listbox virtualization, date picker calendars).

Examples: button, badge, skeleton, progress, alert, avatar, card, label, input, separator, textarea, spinner, visually-hidden, breadcrumb, aspect-ratio, checkbox, radio-group, toggle, switch, slider, accordion, collapsible, tabs, toolbar, scroll-area.

**Archetype B: Adapter-Backed (EXCEPTION ONLY)** (`ariaStateProvider: "meltui"`)
Uses Melt UI adapter through transport chain ONLY when the ARIA/focus/keyboard pattern is too complex for ColdLight to own directly. Must be justified in `contract.ts` with a comment explaining WHY adapter is needed. Root creates adapter + provides context via Symbol-keyed Svelte context. Sub-components consume from context. `ariaStateProvider: "meltui"` in contract triggers scanner to verify adapter impl exists.

**ColdLight is ALWAYS the public API regardless of archetype.** Users never import `@melt-ui/svelte`. The adapter is an internal implementation detail.

Examples (justified by ARIA complexity): dialog, alert-dialog, sheet, combobox, command, context-menu, dropdown-menu, hover-card, menubar, navigation-menu, popover, select, tooltip, date-picker.

## Foundation Requirements (Non-Negotiable)

> These requirements define ColdLight's identity. Every sprint, every task, every line of code must satisfy these. If a change violates any of these, it is wrong. Period.

### A. ColdLight = Sole CSS Authority

1. **ColdLight is the ONLY source of visual CSS.** No hand-written `.css` files exist outside `design/`. No exceptions.
2. **All layout CSS becomes tokens/recipes.** `shell.css` and any other colocated CSS files get deleted. Their content (grid geometry, scrollbar styling, spacing, gaps) is expressed as tokens consumed directly by `.svelte` files via Tailwind utilities or recipe class strings.
3. **Zero colocated `.css` files anywhere.** `.svelte` files consume ColdLight (tokens + recipes + molecules + TW4 utilities) directly. No `import "./styles/whatever.css"` in any component.
4. **CSS is GENERATED by ColdLight**, not hand-authored. `tokens.ts` → `ds-tokens-build.ts` → `tokens.css`. Molecules are `@utility` definitions consuming tokens. Everything else is Tailwind utilities from `@theme`.
5. **CSS is CONTROLLED by ColdLight at runtime** via recipes (`DsSurfaceProps` in → per-slot class strings out) and token references (`var(--token-name)`).

### B. ColdLight = Both TW4 AND Custom JS

6. **ColdLight seamlessly manages Tailwind v4** (utility classes from `@theme` tokens) **AND custom JS** (recipe functions, `DsSurfaceProps`, component props, variant encoding). It is BOTH. Not one or the other.
7. **`.svelte` components can use EITHER** TW4 utility classes directly (`bg-teal-400`, `rounded-lg`) **OR** recipe-driven class strings from `getRecipe(id).classes(props)`. ColdLight orchestrates both paths.
8. **Component v-recipe pattern**: toggle visual categories (surface, motion, depth, glow, bevel) per-component via recipe props. Each category has its own control in VPB.

### C. Schema-Driven, Fully Typed

9. **Everything schema-driven** — Zod validates all contracts, token values, recipe props, block nodes, VPB payloads. If it enters the system, it gets validated.
10. **Fully typed** — complete TypeScript types for every design system contract, prop, token, recipe, slot, state. No `any`. Strict mode.
11. **Style Dictionary v5 token pipeline** — `tokens.ts` → SD5 build → CSS output. DTCG 1.0 format (`$value`, `$type`). SD5 drives the entire token-to-CSS-to-Tailwind pipeline.
12. **Manifest-generating** — catalog contracts + scanner produce `coldlight.manifest.json`. Runtime registry reads only the manifest. VPB reads the manifest for its palette.
13. **No-code compiler patterns** — schema-driven generation, not manual CSS authoring. New tokens → rebuild → new CSS. New primitive → declare contract → scanner validates → manifest updates.

### D. Taxonomy = The Registry Spine

14. **Taxonomy is THE registry spine of ColdLight** — scanner reads contracts FROM their implementations and registers them. No primitive, no recipe, no component exists without a `contract.ts` alongside its implementation.
15. **Every primitive's contract lives at `primitives/{kind}/contract.ts`** — slots, states, ARIA requirements, keyboard maps declared there. Scanner globs this path. NOT in a separate taxonomy folder.
16. **Every component's contract lives at `components/{kind}/contract.ts`** — props, variants, ARIA mapping, token usage declared there. Same scanner glob pattern.
17. **Taxonomy enforcement by code** — Lefthook pre-commit + scanner validates all `contract.ts` files against Zod schemas (`taxonomy/schema/primitive.ts`, `taxonomy/schema/component.ts`). Fails build on: Zod failure, duplicate kind, `ariaStateProvider: "meltui"` without adapter impl.
18. **Pattern for adding anything new**: write `primitives/{kind}/contract.ts` → write `primitives/{kind}/{Kind}.svelte` → write `components/{kind}/contract.ts` → write `components/{kind}/{Kind}.svelte` → scanner registers both → manifest updates → VPB palette updates. The 6-Stage Gate.

### E. Folder Structure — Hypermodular, Strict

19. **Clear categories** in the folder structure: tokens, molecules, variants, svg, typography, focus, scrollbars, keyframes — each in its own directory under `design/`.
20. **Hypermodular strict organized file structure** — each concern in its own file/folder. No god files. No dumping grounds.
21. **Every folder/file follows the established patterns** — no ad-hoc files. If a file doesn't fit a pattern, the pattern is extended or the file doesn't exist.

### F. VPB — Visual Page Builder

22. **VPB uses SvelteFlow nodes** (`@xyflow/svelte`) for the block tree visualization — node hierarchy, slot connections, data flow.
23. **VPB has popup overlay modals per category** with specific sliders and inputs — surface picker, depth slider, glow color, bevel intensity, motion curve, transition timing. Each category gets its own UI panel.
24. **VPB consumes catalog registry** — palette of available kinds, their slots, their allowed recipes ALL generated from `coldlight.manifest.json`. Nothing hardcoded.
25. **VPB controls full props and children props** (Svelte snippets) — every prop on `DsSurfaceProps` has a UI control. Children/slots are managed via the node graph.
26. **Proactive UI** — tooltips explain each control, suggestions for common combinations, block invalid prop combinations before they happen, show warnings for accessibility violations.

### G. ARIA + Accessibility

27. **Full ARIA** — every primitive has complete accessibility. Roles, states (`aria-expanded`, `aria-selected`, etc.), keyboard navigation (arrow keys, escape, enter, tab). Declared in catalog contracts, enforced by scanner. ColdLight owns ARIA directly via WAI-ARIA APG patterns.
28. **Modern UI with full props and children props** — clean component API driven by typed interfaces. Every prop is typed. Every slot is typed. Every event is typed.

### H. Enforcement

29. **Biome configured** to lint all TypeScript/Svelte. CSS linting blocks violations (no raw CSS outside `design/`).
30. **Lefthook pre-commit guards**: no `--dp-`/`--cl-` prefixes, no colocated `.css` files outside `design/`, no undeclared catalog kinds, token validation, svelte-check.
31. **Scanner (build-time)** verifies parity between catalog contracts and actual primitives/recipes. Missing primitive? Missing adapter? Missing recipe? Build fails.
32. **CI/CD token build** — automate `ds-tokens-build.ts` in pipeline. Tokens change → CSS regenerated → types regenerated → commit includes generated output.

### I. Process

33. **Research → sprint plan → execute.** Never touch code without a sprint document. Planning skill produces research doc + sprint plan. User approves. Then execute.
34. **Pre-release state** — establishing the foundation, not maintaining an app. Every decision is about getting the system RIGHT, not shipping features.
35. **Enterprise design system that scales** — patterns that work for 5 components work for 500. Schema-driven, manifest-generating, scanner-enforced. No shortcuts.

## Token System

### SSOT: `tokens/tokens.ts`

All other token files are GENERATED. Never edit `tokens.css` or `types.ts` directly.

```bash
pnpm ds:tokens:build    # One-shot generation
pnpm ds:tokens:watch    # Watch mode during dev
```

### 3-Tier Token Architecture

Every major design system (Material Design 3, Adobe Spectrum, Salesforce Lightning, IBM Carbon) uses 3 tiers:

```
TIER 1: Global Tokens (raw values — tokens.ts)
  --color-teal-500, --glass-void, --shadow-z2, --duration-fast

TIER 2: Semantic Tokens (intent-based aliases — semantic.ts)
  --surface-primary: var(--glass-void)
  --surface-elevated: var(--glass-smoke)
  --border-subtle: oklch(from var(--color-teal-700) l c h / 0.22)
  --depth-panel: var(--shadow-z2)
  --transition-ui: var(--duration-fast) var(--ease-out)

TIER 3: Component Tokens (scoped to primitive kinds — components.ts)
  --button-bg: var(--surface-primary)
  --button-border: var(--border-subtle)
  --panel-depth: var(--depth-panel)
  --input-border-focus: var(--border-emphasis)
```

**Schema enforcement:** Tier 2 MUST reference Tier 1. Tier 3 MUST reference Tier 2. Raw values only in Tier 1.

### Target Token Format (Channel-Separated OKLCH)

Channel-separated objects enable programmatic color manipulation -- alpha variants, lightness shifts, chroma adjustments -- without string parsing:

```typescript
interface OklchColor {
  l: number;  // 0-1 (lightness)
  c: number;  // 0-0.4 (chroma)
  h: number;  // 0-360 (hue)
  a?: number; // 0-1 (alpha, optional)
}

    50:  { l: 0.97, c: 0.02, h: 180 },
    500: { l: 0.55, c: 0.18, h: 180 },
    900: { l: 0.24, c: 0.07, h: 180 },

```

## Taxonomy System

### PrimitiveContract

Every primitive is specified by a contract at `primitives/{kind}/contract.ts` — the contract lives WITH the implementation. The scanner reads this file, validates it against `taxonomy/schema/primitive.ts` (Zod), and registers the kind into the manifest. The contract declares:

- **kind** -- literal identifier (`"dialog"`, `"button"`)
- **ariaStateProvider** -- `"meltui"` or `"coldlight"`
- **slots** -- required, optional, forbidden
- **slotSpec** -- per-slot HTML element, children mode, ARIA requirements
- **states** -- shared and primitive-specific state tokens
- **slotStates** -- which states each slot can have
- **slotActions** -- per-slot action declarations
- **aria** -- role, required/optional ARIA attributes
- **keyboard** -- interaction keys
- **focusStrategy** -- how focus is managed
- **compound** -- whether sub-components share context
- **orientation** -- navigation axis (if applicable)
- **dismissBehavior** -- how overlays close (if applicable)

Contracts are adapter-agnostic. They don't care which provider fulfills them.

### Scanner + Manifest

Build-time scanner (`taxonomy/scanner.ts`) globs `primitives/*/contract.ts` + `components/*/contract.ts`, validates each against Zod schemas, flags duplicate kinds, and writes the manifest.

- `ariaStateProvider: "coldlight"` — validates primitive + component exist
- `ariaStateProvider: "meltui"` — additionally validates MeltUI adapter impl exists

Scanner outputs `taxonomy/.generated/manifest.json`. Runtime registry (`taxonomy/registry.ts`) reads only this manifest — no filesystem scanning at runtime. O(1) Map lookups.

### Data Attributes

All primitive elements emit:

| Attribute | Required | Example |
|-----------|----------|---------|
| `data-kind` | Always | `"dialog"` |
| `data-slot` | Always | `"content"` |
| `data-state` | If stateful | `"open"` |
| `data-id` | If user provides | `"my-dialog"` |

Recipe-driven attributes:

| Attribute | Purpose | Example |
|-----------|---------|---------|
| `data-surface` | Surface type | `"glass"`, `"matte"`, `"solid"` |
| `data-material` | Material variant | `"void"`, `"deep"` |
| `data-motion` | Motion state | `"idle"`, `"hover"` |
| `data-focus` | Focus state | `"ring"`, `"glow"` |

## Recipe System

### Recipe Definition

A recipe is a composable configuration with defaults that produces CSS class strings per slot:

```typescript
interface RecipeDefinition<Props extends DsSurfaceProps> {
  id: RecipeId;
  kind: BlockKind;
  label: string;
  defaults: Props;
  classes: (props: Props) => Record<string, string>;
  requires?: ActionId[] | ((props: Props) => ActionId[]);
}
```

### DsSurfaceProps (Composable Schema)

Each prop becomes a VPB UI control:

```typescript
interface DsSurfaceProps {
  color: { a: ColorToken; b?: ColorToken };
  finish: FinishToken;       // glass, matte, solid
  frame: FrameToken;         // none, soft, hard, crisp
  depth: DepthToken;         // z0-z4
  motion: { hover?: MotionToken; enter?: MotionToken; ambient?: MotionToken };
  bevel: { level: BevelToken };
  glow: { color?: GlowToken; intensity?: number };
}
```

### Action Composition

Renderers use `use:applyRecipeActions` to auto-attach required Svelte actions:

```typescript
const actionRegistry = { glowTrack, ripple } as const;
type ActionId = keyof typeof actionRegistry;

export function applyRecipeActions(
  node: HTMLElement,
  recipe: RecipeDefinition
): ActionReturn {
  const cleanups: (() => void)[] = [];
  for (const id of recipe.requires ?? []) {
    const action = actionRegistry[id];
    if (action) {
      const result = action(node);
      if (result?.destroy) cleanups.push(result.destroy);
    }
  }
  return { destroy() { cleanups.forEach(fn => fn()); } };
}
```

If a recipe declares `requires`, the renderer MUST attach those actions. No manual JS effects.

## Variant Key System

Compact class encoding of recipe surface parameters. Both individual segments and combined strings supported.

### Encoding

| Key | CSS Variable | 0 | 1 | 2 | 3 | 4 |
|-----|-------------|---|---|---|---|---|
| `s` | `--v-surface` | transparent | glass-void | glass-deep | glass-smoke | glass-frost |
| `z` | `--v-depth` | none | z1 | z2 | z3 | z4 |
| `l` | `--v-layers` | flat | bevel-subtle | bevel-soft | bevel-medium | bevel-strong+filter |
| `t` | `--v-transition` | 0ms | 50ms | 150ms | 250ms | 400ms |
| `m` | `--v-motion` | none | ease-out | ease-inOut | spring | bounce |

### Usage

```html
<!-- Individual segments (composable, override-friendly) -->
<div class="v-s1 v-z2 v-t2">...</div>

<!-- Combined (compact, recipe-emitted) -->
<div class="v-s1z2l0t2m0">...</div>
```

Both forms set the same CSS custom properties. Elements with variant keys automatically consume them:

```css
background: var(--v-surface, transparent);
box-shadow: var(--v-depth, none), var(--v-bevel, none);
transition-duration: var(--v-transition, 0ms);
transition-timing-function: var(--v-motion, linear);
```


## CSS Rules (Strict)

### What's Allowed

- Token references: `var(--glass-void)`, `var(--shadow-z2)`, `var(--color-teal-500)` (unprefixed)
- Semantic token references: `var(--surface-primary)`, `var(--border-subtle)`, `var(--depth-panel)`
- Component token references: `var(--button-bg)`, `var(--panel-border)`
- Tailwind @theme utilities: `bg-glass-void`, `shadow-z2`, `rounded-md`
- Data attributes: `data-surface="glass"`, `data-kind="panel"`
- Variant key classes: `v-s1`, `v-z2`, `v-s1z2l0t2m0`
- Molecule utility classes: `.glass-void`, `.glow-teal`, `.bevel-soft`

### What's Banned

| Violation | Why |
|-----------|-----|
| Raw colors (`#fff`, `oklch()`, `rgb()`, `hsl()`) outside `tokens.ts` | All color through tokens |
| Arbitrary Tailwind (`bg-[#000]`, `text-[12px]`) | All values from @theme |
| Inline styles (`style="..."`) | Recipes handle all styling |
| `<style>` blocks in primitives | Primitives are unstyled |
| Raw `<button>`, `<input>`, `<dialog>` when a ColdLight primitive exists | Use the primitive |
| Emoji icons in production UI | Use SVG icon components |
| Prefixed CSS variables | Token prefix is NONE (unprefixed) |

### Ephemeral Computed Vars

Allowed ONLY with `--_` prefix (private internal vars, e.g. `--_shadow-glass`, `--_mouse-x`), in allowlisted files (molecules, actions). The `--_cl-*` prefix is **banned** (legacy). Use bare `--_` prefix instead.

### CSS Entry Point

`app.css` imports Tailwind, fonts, and `design/index.css`. The design barrel imports in order:
1. `tokens/tokens.css` (generated — all 3 tiers as CSS custom properties + @theme block)
2. `molecules/*.css` (glass, glow, bevel, sheen, grid, void, tracked, depth)
3. `variants/variant-keys.css` (variant key utility classes)
4. `svg/filters.css` (SVG filter utility classes)
5. `typography/typography.css`
6. `focus/focus.css`
7. `scrollbars/scrollbars.css`
8. `keyframes/keyframes.css`

## VPB (Visual Page Builder)

Dev-only tool at `src/lib/sys/debug/vpb/`.

### Flow

1. Reads recipe registry + catalog contracts
2. Shows dropdown/slider controls per DsSurfaceProps field
3. User modifies props -> calls `classes()` with new props -> preview updates
4. User saves as new recipe variant -> registered platform-wide
5. VPB generates Svelte code
6. Build pipeline generates CSS from all registered recipes

### Node Graph (SvelteFlow)

VPB uses `@xyflow/svelte` for node-based composition visualization -- block hierarchy, slot connections, data flow.

### Block Storage

VPB persists `BlockNode[]` trees. No theme values, no CSS, no classnames in stored data. Runtime validation (Zod) on load catches schema drift before it breaks the UI.

## Transport Chain (Melt UI Cloaking — EXCEPTION ONLY)

Most primitives are ColdLight-owned (Archetype A) and have NO adapter chain. For the rare Archetype B exceptions:

```
@melt-ui/svelte                           <-- ORIGIN (never imported by components)
    |
    v
api/adapters/meltui/_internal/            <-- Provider Internals (exception-only)
    |
    v
primitives/{kind}/{Kind}.svelte           <-- ColdLight public API
```

Zero `@melt-ui/svelte` imports outside `_internal/`. If you see a direct Melt import in a primitive, it's a violation.

## 6-Stage Gate (Before Any .svelte Renderer)

1. **Stage 0 — Naming + Intent:** Kind name exists, purpose documented, slots defined
2. **Stage 1 — Token Check:** Uses existing tokens, new tokens added to SSOT only, `pnpm ds:tokens:build` run
3. **Stage 2 — Primitive Contract:** `primitives/{kind}/contract.ts` written, satisfies `PrimitiveContractSchema`. `primitives/{kind}/{Kind}.svelte` written — zero ARIA applied, full prop spread, `data-kind`, `data-slot`.
4. **Stage 3 — Component Contract:** `components/{kind}/contract.ts` written, satisfies `ComponentContractSchema`. `components/{kind}/{Kind}.svelte` written — wraps primitive, computes ARIA from state, zero visual style.
5. **Stage 4 — Recipe Authoring:** Recipe ID in registry, variants mapped to Tailwind classes (token-backed only via @theme)
6. **Stage 5 — VPB Registration:** Block in palette, default recipe + props, property UI config
7. **Stage 6 — UI Layer:** `ui/{kind}/{Kind}.svelte` created — wraps component, applies recipe classes. Project-specific.

If any stage fails: **STOP. Fix registry first.**

## SD5 CSS Rule (ABSOLUTE)

**Nothing touches CSS directly. Everything goes through SD5.**

```
tokens.ts (SSOT) → SD5 pipeline → tokens.css + tailwind.css + types.ts
                                        ↓               ↓
                               :root { --token }    @theme { --color-* }
                                        ↓               ↓
                               var(--token-name)    bg-teal-500 (Tailwind utility)
```

- **Raw color values** exist ONLY in `tokens.ts`. Nowhere else.
- **CSS custom properties** exist ONLY in `tokens.css` (SD5 generated). Never hand-authored.
- **@theme** exists ONLY in `tailwind.css` (SD5 generated). Never hand-authored.
- **Recipe class names** MUST map to tokens in @theme. No hardcoded values.
- **Molecules** use ONLY `var(--token-name)` references. Zero raw values.

**ColdLight is the public API. Users never see adapters.**
