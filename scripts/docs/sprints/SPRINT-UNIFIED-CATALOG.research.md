# Research: ColdLight Unified Catalog — Aligning Code to Vision

**Date**: 2026-03-02
**Sprint**: UNIFIED-CATALOG
**Status**: COMPLETE

---

## Question/Goal

The owner's vision: ColdLight is a config-driven, schema-driven, ID-cataloged design system where ONE unified manifest catalogs every primitive, component, recipe, preset, effect, and token — organized by clean sections (ARIA, SEO/metadata, styling, effects). VPB consumes this manifest to provide layman-rich UI with wizards, AI guidance, composable presets and effects. The system is framework-agnostic at its core (attunes to Svelte, TSX, etc via config), and everything auto-grows when you add to the SSOT.

**The question: Is any of this actually built? What's real vs theater?**

## Real-World Design System Patterns (2026)

### shadcn Registry (v3, 2025-2026)
The gold standard for component cataloging:
```json
{
  "$schema": "https://ui.shadcn.com/schema/registry.json",
  "name": "acme",
  "items": [{
    "name": "button",
    "type": "registry:component",
    "title": "Button",
    "description": "A clickable button.",
    "registryDependencies": ["icon"],
    "dependencies": [],
    "files": [{ "path": "button.tsx", "type": "registry:component" }],
    "cssVars": { "theme": {}, "light": {}, "dark": {} },
    "css": { "@layer base": "...", "@utility": "..." },
    "categories": ["action", "form"],
    "meta": { "docs": "...", "figma": "..." }
  }]
}
```
**Key insight**: Every item is a complete package — dependencies, CSS, tokens, metadata, categories. Framework-agnostic schema. CLI resolves dependencies and transforms imports.

### Ark UI Anatomy (@ark-ui/anatomy)
```typescript
const buttonAnatomy = createAnatomy("button").parts("root", "label", "icon");
// Returns: { root: "button__root", label: "button__label", icon: "button__icon" }
```
**Key insight**: Machine-readable slot list drives styling recipes, ARIA mapping, AND manifest. The anatomy IS the contract.

### Ark UI + Zag.js ID System
```
{rootId}:trigger:{itemId}
{rootId}:content:{itemId}
```
**Key insight**: User provides root ID OR auto-generate. All sub-part IDs derive deterministically. Scoped, no collisions by construction.

### Figma Schema 2025
Unified foundation: tokens, themes, components, and variables all accessible through one API. Single centralized manifest.

## GAP ANALYSIS: Vision vs Reality

### Owner's Requirement 1: "Unified manifest with every component cataloged with ID"
**Status: DOES NOT EXIST**
- Token manifest has encoding categories but zero components
- Scanner manifest is empty (parity blocks it)
- No component has a catalog-style ID
- No unified manifest combines tokens + components + recipes + effects + presets

### Owner's Requirement 2: "data-kind, data-slot, data-variant with child props listed"
**Status: PARTIALLY EXISTS**
- `data-kind` and `data-slot` work on every primitive ✅
- `data-variant` added to config but NOT rendered in DOM ❌
- "child props listed" — the contract.slotSpec defines slots + element + children mode, but this is TypeScript only. Not in any manifest. Not queryable by VPB. ❌

### Owner's Requirement 3: "Clean sections for ARIA control, SEO/metadata, styling, effects"
**Status: DOES NOT EXIST as a catalog**
- Contracts have ARIA requirements per slot ✅ (in TypeScript)
- No SEO/metadata section exists anywhere ❌
- Styling via recipes works ✅ (in code)
- Effects exist ✅ (in code)
- **None of this is in a manifest/catalog that VPB can consume** ❌

### Owner's Requirement 4: "Presets/colors/effects generated during dev, composable/assignable via UI"
**Status: PARTIALLY WORKS**
- Token pipeline generates CSS ✅
- @utility encoding classes work ✅
- 50 presets exist ✅
- **But VPB can't read any of this** because the manifest it reads is empty ❌
- No UI for assigning presets/effects ❌

### Owner's Requirement 5: "Config declares framework, ColdLight attunes itself"
**Status: CONFIG EXISTS, ATTUNING DOES NOT**
- `coldlight.config.ts` declares adapters, attributes, generation, enforcement ✅
- Config says "meltui" adapter ✅
- But the import cloak (`.generated/imports.gen.ts`) is empty ❌
- No mechanism to attune to TSX or another framework ❌

### Owner's Requirement 6: "Everything auto-grows — add to SSOT, run build, folders/manifest/registry follow"
**Status: BROKEN**
- Token categories auto-grow ✅ (add to token-categories.ts → types.ts + variants.css update)
- Primitive contracts don't auto-grow ❌ (scanner fails, manifest stays empty)
- Adding a contract does NOT produce folders/manifest entries because scanner is blocked

### Owner's Requirement 7: "Enterprise-grade IDs, schema-driven, no duplicates"
**Status: COSMETIC CHANGE ONLY**
- I changed the ID format string to `cl-{kind}-{slot}-{instance}`
- But it's still a module-level counter. Not schema-driven. Not cryptographically unique.
- No duplicate detection. No scope isolation for SSR/hydration. Just a format change.

## ROOT CAUSE

**The scanner is the linchpin.** It was built to read all 89 contracts, validate parity, and produce the unified `ColdLightManifest` that VPB consumes. But `failOnParity: true` + 52 missing primitive implementations = scanner returns null. The manifest has been empty since Feb 16.

Everything downstream — VPB manifest consumption, component catalog UI, AI-guided suggestions, wizard-driven composition — is dead because the manifest they'd read is empty.

**The token pipeline works independently** (SD5 → tokens.css/tailwind.css/variants.css) but it only produces token data, not component catalog data.

## RECOMMENDATIONS

### P0: Produce a REAL unified manifest
Two approaches:
1. **Fix the scanner**: Either implement the 30 missing primitives (contract-only kinds that need .svelte stubs), OR make parity errors non-fatal (collect errors but still emit the manifest for the 37 primitives that ARE complete)
2. **Merge the two manifests**: The token manifest has encoding/token data. The scanner manifest has component/primitive data. One unified manifest should have BOTH.

**Recommended: Option 1B** — Make parity errors warnings, not blockers. Emit the manifest with what's available. Mark incomplete kinds as `status: "contract-only"`. This unblocks everything immediately.

### P1: Unified manifest schema (shadcn-inspired)
Design ONE manifest that a VPB panel can consume:
```json
{
  "$schema": "coldlight/manifest",
  "version": "1.0.0",
  "config": { "framework": "svelte5", "adapter": "meltui" },
  "tokens": { /* encoding categories, token enums, generated files */ },
  "primitives": [{
    "kind": "button",
    "id": "cl:primitive:button",
    "status": "complete",  // or "contract-only"
    "contract": {
      "slots": { "required": ["root"], "optional": ["icon","label"] },
      "slotSpec": { "root": { "element": "button", "children": "snippet" } },
      "aria": { "role": "button", "required": [], "optional": ["aria-pressed"] },
      "keyboard": ["Enter","Space"],
      "states": { "shared": ["disabled","hover"], "specific": ["pressed","loading"] }
    },
    "builder": "coldlight",
    "dataAttributes": ["data-kind=button", "data-slot=root"],
    "presets": ["btn-primary","btn-secondary","btn-ghost","btn-danger","btn-outline"],
    "recipes": ["button.glass.void"],
    "categories": ["action","form"]
  }],
  "components": [{ /* same shape + primitiveKind ref */ }],
  "recipes": [{ /* id, kind, label, defaults, slot classes */ }],
  "presets": [{ /* id, encoding values per category */ }],
  "effects": [{ /* id, category, classes, triggers */ }]
}
```

### P2: Wire data-variant and data-id to actual DOM
Every component needs to render:
```svelte
<ButtonRoot
  data-variant={visual.variant}
  data-id={builder.ids.root}
  ...
>
```
This is mechanical — update each component .svelte file. 82 components.

### P3: Build pipeline produces unified manifest
`pnpm ds:build` should:
1. Run SD5 → tokens, variants, typography, etc.
2. Run scanner (parity=warn) → collect primitives, components, recipes, effects
3. Merge both into ONE `coldlight.manifest.json`
4. Write to `generated/coldlight.manifest.json`
5. VPB reads this single file

### P4: Framework attuning
The config declares "svelte5" but nothing reads it. The import cloak was supposed to map adapter-specific imports to generic names. This needs implementation so ColdLight can theoretically attune to TSX.
