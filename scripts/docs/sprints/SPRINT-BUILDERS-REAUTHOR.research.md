# Research: ColdLight Builder Re-Authoring to MeltUI Gold Standard

**Date**: 2026-02-26
**Sprint**: SPRINT-BUILDERS-REAUTHOR
**Status**: COMPLETE

---

## Question/Goal

ColdLight has 55 builders and ~50 components generated by agents. All builders return `SlotAttrs` (`Record<string, unknown>`) instead of exact typed return objects. This makes TypeScript inference useless — the generated `.d.ts` declarations would show generic `Record<string, unknown>` instead of precise attribute shapes.

**Goal**: Understand the exact quality gap between ColdLight builders and MeltUI builders, then plan a re-authoring sprint that brings ColdLight builders to MeltUI's quality standard.

---

## MeltUI Builder Architecture (Gold Standard)

Studied 11 MeltUI `.d.ts` files: Accordion, Dialog, Tabs, Combobox, Select, Toggle, Progress, RadioGroup, Avatar, Collapsible, Popover.

### Pattern Summary

**1. Exact Typed Return Objects (NOT generic Record)**

Every slot getter returns an exact object literal type. TypeScript infers precise shapes:

```typescript
// MeltUI — EXACT typed returns
get root(): {
  "data-melt-accordion-root": string;
  id: string;
}

get trigger(): {
  "data-melt-accordion-trigger": string;
  disabled: true | undefined;
  "aria-disabled": boolean | undefined;
  "aria-expanded": boolean;
  "data-disabled": "" | undefined;
  "data-value": string;
  "data-state": string;
  onclick: () => void;
  onkeydown: (e: KeyboardEvent) => void;
}
```

**2. Generics Where Appropriate**

NOT everywhere — only where the type parameter matters to the consumer:

| Builder | Generics | Reason |
|---------|----------|--------|
| `Accordion<Multiple extends boolean = false>` | Yes | `value` type changes (string vs Set) |
| `Tabs<T extends string = string>` | Yes | Tab value type flows through getters |
| `Combobox<T, Multiple extends boolean = false>` | Yes | Option value type + selection mode |
| `Select<T, Multiple extends boolean = false>` | Yes | Same as Combobox |
| `Toggle` | **No** | Boolean value, no polymorphism |
| `Progress` | **No** | Number value, no polymorphism |
| `Collapsible` | **No** | Boolean open, no polymorphism |
| `Avatar` | **No** | String src, no polymorphism |
| `Dialog` | **No** | Boolean open, no polymorphism |

**Takeaway**: Generics ONLY for multiple selection modes or typed value parameters. Simple boolean/string state = no generics.

**3. Helper Methods for Programmatic Control**

Every builder with state that consumers might toggle programmatically:

| Builder | Helpers |
|---------|---------|
| `Accordion` | `isExpanded(id)`, `expand(id)`, `collapse(id)`, `toggleExpanded(id)` |
| `Combobox` | `isSelected(value)`, `select(value)`, `scrollIntoView()`, `highlight()`, `highlightNext/Prev/First/Last()` |
| `RadioGroup` | `select(item)` |
| `Select` | `isSelected(value)`, `select(value)` |
| `Toggle` | value getter/setter |
| `Dialog` | open getter/setter |
| `Collapsible` | open getter/setter |

**4. Sub-Classes for Compound Patterns**

When a builder has repeated per-item state (not just per-item attributes):

| Builder | Sub-Class | Has Own Typed Getters |
|---------|-----------|----------------------|
| `Accordion` | `AccordionItem<Meta, Multiple>` | `heading`, `trigger`, `content` + `isExpanded`, `expand()`, `collapse()`, `toggleExpanded()` |
| `RadioGroup` | `RadioItem` | `attrs` getter + `value`, `checked` properties |
| `Combobox` | — (uses `getOption()` method) | Returns typed object |

**Takeaway**: Sub-classes when items have their own reactive state (isExpanded, isChecked). Method returns when items are pure attribute bags.

**5. Inheritance for Shared Popup/Overlay Logic**

| Base | Children | Shared |
|------|----------|--------|
| `BasePopover` | `Popover`, `Combobox`, `Select` | open state, floating config, focus management, escape/outside-click, shared `onfocus`/`onfocusout` |

**6. Typed IDs**

```typescript
ids: {
  heading: string;
  root: string;
  item: string;
  trigger: string;
  content: string;
}
```

Not `Record<string, string>` — exact named keys.

**7. JSDoc**

Every public property and method has JSDoc. Props types have `@default` annotations.

**8. `.d.ts` Files are AUTO-GENERATED**

CRITICAL: MeltUI's `.d.ts` files are NOT hand-written. They're auto-generated by the TypeScript/Svelte compiler during `svelte-package` build. The `.svelte.ts` source has precise enough types that the compiler generates exact declarations.

ColdLight builders are source code (not a published package). They don't need hand-written `.d.ts` files. What they need is TypeScript source typed precisely enough that auto-generated declarations would be as precise as MeltUI's.

**When ColdLight returns `SlotAttrs` (`Record<string, unknown>`), the auto-generated `.d.ts` shows `Record<string, unknown>` — useless. When ColdLight returns exact typed objects, the auto-generated `.d.ts` shows precise attribute shapes — matching MeltUI quality.**

### Fundamental Problems

**Problem 1: `SlotAttrs` = `Record<string, unknown>`**

EVERY builder returns `SlotAttrs` for EVERY getter. This single type alias destroys all type precision:

```typescript
// ColdLight — BROKEN generic return
get root(): SlotAttrs {
  return {
    [metadata.dataAttrs.root]: "",
    id: this.ids.root,
    role: "button",
    "aria-disabled": disabledAttr(this.disabled),
    // ... TypeScript INFERS the exact type here but it's CAST to SlotAttrs
  };
}
```

TypeScript naturally infers the exact object literal type from the return expression. But annotating the return as `SlotAttrs` (`Record<string, unknown>`) throws that away. **Remove the return type annotation and TypeScript infers the exact type automatically.**

**Problem 2: No Helper Methods**

Checkbox has `toggle()` but most builders lack programmatic control methods:
- ToggleGroup: no `isSelected()`, `select()`, `deselect()`
- Button: no programmatic `press()` for toggle mode
- Table: no `sort()`, `getHeaderCell()` with typed sort state

**Problem 3: No Sub-Classes**

ToggleGroup's `getItem()` returns `SlotAttrs`. Should return a typed item class with `isPressed`, `toggle()`.

**Problem 4: No Inheritance**

No base overlay/popup class. When dialog, sheet, popover, dropdown builders are written, they'll each duplicate escape/outside-click/focus-trap logic.

**Problem 5: Sparse JSDoc**

Some builders have good header doc but lack per-method/per-property JSDoc.

## The Fix: Technical Approach

### Step 1: Kill `SlotAttrs`

In `_internal/types.ts`:
- DELETE `SlotAttrs = Record<string, unknown>`
- Every builder getter: REMOVE the `: SlotAttrs` return type annotation
- TypeScript inference produces exact typed returns automatically
- Export a utility type for external consumers who need to accept any builder output:
  ```typescript
  export type BuilderAttrs = Record<string, unknown>;
  ```

### Step 2: Return Type Precision

For builders where inference alone isn't enough (computed properties, conditional attrs):
- Use explicit return type annotations with exact shapes
- Use `as const` satisfies where helpful

### Step 3: Add JSDoc

Every public property, getter, method, constructor param gets JSDoc.

### Step 4: Add Helper Methods

Per builder as specified in Category B/C analysis above.

### Step 5: Add Sub-Classes

For compound builders with per-item reactive state (ToggleGroup, Steps, etc.).

### Step 6: BaseOverlay Pattern

Create `_internal/base-overlay.svelte.ts` for shared popup logic. Sheet, notification-center extend it.

## Recommendations

### Approach: In-Place Rewrite, NOT Delete-and-Recreate

The builder logic (state management, keyboard handling, ARIA computation) is CORRECT. The problem is purely the TYPE LAYER — `SlotAttrs` casts away all type precision.

**Recommended approach:**
1. Kill `SlotAttrs` type alias
2. Remove `: SlotAttrs` return type annotations from all getters
3. TypeScript inference immediately produces exact types
4. Add JSDoc, helpers, sub-classes as needed per category
5. Verify with `svelte-check`

This is MORE EFFICIENT and LESS RISKY than delete-and-recreate because:
- Builder logic is tested (1,286 passing tests)
- Only the type annotations are wrong, not the runtime behavior
- Deleting working code to rewrite identical logic wastes effort
- The fix for 29 simple builders is literally removing `: SlotAttrs` from each getter

### Schema Fixes Still Needed

From the 117 svelte-check errors:
- StateTokenSchema: add `"loaded"`, `"inactive"`
- AriaRoleSchema: add `"table"`, `"row"`, `"rowgroup"`, `"cell"`, `"columnheader"`, `"rowheader"`
- FocusStrategySchema: `"roving-tabindex"` → `"roving"` in 2 contracts
- Component types: Omit null-bearing HTML props
- Test files: `as HTMLElement | null` casts

These are still valid fixes needed alongside the builder rewrite.
