## Pre-Sprint: SSOT Consolidation

Before any code, these duplicates must be resolved.

### STOP 1 — Owner Decision Required: Hook Consolidation

**Question**: Which button hook is the SSOT?

**Option A**: Keep `useButton()` (coldlight/primitives/button/use-button.svelte.ts)
- Svelte 5 runes native ($state, $derived)
- Getter-wrapped return (immutable public API)
- 109 lines, more sophisticated
- Lives in the primitive layer where S2 puts behavior

**Option B**: Keep `createButton()` (api/dsadapters/coldlight/_internal/button/index.ts)
- Plain function, getter-fn args pattern
- 105 lines, simpler
- Lives in dsadapters where the component currently imports from
- Name matches S2 convention (createX)

**Option C**: Merge into one — take the best of both, put it where it belongs.

**Impact**: Every component follows whichever pattern we pick. This sets the hook convention for all 89 kinds.

---

### STOP 2 — Owner Decision Required: Primitive Layer

**Question**: What is the relationship between `coldlight/primitives/button/` and `primitives/button/`?

**Current state**:
- `coldlight/primitives/button/` has 7 files: component, props, types, a11y spec, anatomy, hook, barrel
- `primitives/button/` has 1 file: bare `<button>` with data-kind/data-slot (the Shard)

**Option A**: `coldlight/primitives/button/` is the full primitive (behavior + structure + specs). `primitives/button/` is the public Shard (structural shell only). Two layers, both needed.

**Option B**: Consolidate into one location. Move specs (a11y, anatomy, types) into the Shard folder. Delete `coldlight/primitives/button/`.

**Option C**: `coldlight/primitives/button/` becomes the package-internal reference. `primitives/button/` is the public API that wraps it.

**Impact**: Sets the folder structure for all 89+ component kinds. Package-ready design folder depends on this.

---

### STOP 3 — Owner Decision Required: Recipe Unification

**Question**: Should `buttonRecipe()` (structural) and `recipes/components/button/` (visual) be one call or two?

**Current state**:
- `components/button/recipe.ts` → `buttonRecipe('md')` returns height/padding/gap classes
- `recipes/components/button/button.default.ts` → registers "button.glass.void" with recipe engine, emits v-* segments
- Component calls `buttonRecipe()` for structure AND `useColdLight()` for visual separately

**Option A**: Keep separate. Structural recipe is co-located with component. Visual recipe lives in recipe engine. Component composes both. Clear separation.

**Option B**: Merge into one recipe call. `buttonRecipe({ intent: 'primary', size: 'md' })` returns ALL classes — structural + visual. Single call, single source.

**Option C**: Structural sizing becomes part of the token system (DTCG dimension composites per size). Recipe only handles visual. Size tokens in SD5 → recipe consumes everything from tokens.

**Impact**: Defines how every component resolves its styles. This is the recipe architecture decision.

---

### STOP 4 — Owner Decision Required: Data Attributes vs Classes

**Question**: Should ColdLight components use data-attribute selectors or Tailwind classes for visual styling?

**EFFINGAI reference uses**: `data-variant="primary"` + CSS rules targeting `[data-variant="primary"]`
**Current DevPulse uses**: Tailwind utility classes assembled by recipe + useColdLight()

**Option A**: Tailwind classes (current). Recipes return class strings. `cn()` merges them. Tailwind processes.

**Option B**: Data attributes (EFFINGAI pattern). Components set `data-*` attributes. CSS rules generated by SD5 target `[data-*]` selectors. No Tailwind arbitrary values ever.

**Option C**: Hybrid. Data attributes for state (data-disabled, data-pressed) + token-backed Tailwind utilities for visual (no arbitrary values).

**Impact**: Fundamental styling architecture. Affects every component, every recipe, SD5 output format.
