# SPRINT: Visual Glass System -- Tokenize Hardcoded CSS

**Status**: READY
**Priority**: P0
**Prerequisite**: Token pipeline working (`pnpm ds:tokens:build`)
**Research**: `SPRINT-VISUAL-GLASS-SYSTEM.research.md`

## Goal

Move all hardcoded visual CSS from `app.css` into the ColdLight token/recipe/preset system.
Every value below is currently in `app.css` as raw CSS. Each must become a token, preset value, or recipe slot class.

---

## Architecture Decision (from research)

**Approach**: Update existing tokens + add 2 hue-tinted surfaces + 2 accent frames.
**NOT**: per-component tokens, CSS custom property hue params, or a 9th encoding axis.

**Key principles:**
1. Surface tokens = reusable palette (not per-component)
2. Hue-tinted glass = genuinely different surfaces (glass-teal, glass-purple)
3. Panel hierarchy = recipe-level (frame/bevel treatment), not token-level
4. Small per-slot adjustments = recipe structural classes

## DO NOT

- Do not create per-component tokens (glass-topbar, glass-sidebar, etc.)
- Do not add a 9th encoding axis for hue
- Do not parameterize glass with var(--hue) CSS custom properties
- Do not delete backdrop patterns from app.css (separate scope)
- Do not change any component API -- only token values, presets, recipe internals
- Do not run ds:tokens:build until Phase 1 tokens are authored in tokens.css
- Do not remove hardcoded CSS until pipeline equivalents are verified working
